A1e. ANALISIS ctx.r12 vs R12D (menjawab syarat #2 dan #4)
==============================================================================
TEMUAN DARI _docs.pluto:
  * OWH mengekspos ctx.r12 — yaitu register 64-bit penuh.
  * Dokumen TIDAK menyediakan ctx.r12d, ctx.r8d, ctx.eax, dst.
    Semua register diekspos dalam lebar 64-bit.

  Jadi 'R12D' yang kamu tanyakan = 32-bit RENDAH dari ctx.r12.
  Bukan sesuatu yang bisa diset langsung — harus dihitung.
------------------------------------------------------------------------------
KONSEKUENSI PENTING (mengacu pada A1/A2 di Bagian D1):
  1. Kalau kamu menulis nilai 32-bit ke r12, x86-64 MENOLKAN
     bit 32..63. Jadi bit atas yang tadinya tidak nol akan hilang.
  2. Kalau r12 menyimpan POINTER 64-bit dan kamu hanya memotong
     32-bit rendahnya, pointer itu HANCUR. Ini alasan kuat
     mengapa G1/G2 wajib dibuktikan lebih dulu.
  3. Menulis 32-bit rendah tanpa merusak bit atas butuh operasi
     masking, bukan sekadar perkalian.
------------------------------------------------------------------------------
CONTOH ARITMETIKA (murni hitungan, tidak menyentuh game):
  nilai 64-bit penuh : 4294967396  (bit atas=1, 32-bit rendah=100)
  low32 (R12D)       : 100
  ganti rendah jadi 300, bit atas dipertahankan -> 4294967596
  bandingkan: mengalikan SELURUH nilai 64-bit ikut mengubah bit atas
              (contoh: 4294967396 x3 = 12884902188)  <-- bukan yang diinginkan
------------------------------------------------------------------------------
CATATAN TAMBAHAN DARI DOKUMEN:
  * ctx.xmm0..xmm15 diekspos sebagai float 32-bit rendah.
    Kalau jumlah loot disimpan sebagai FLOAT, maka register yang
    relevan adalah xmm, BUKAN r12. Ini harus dibuktikan dulu.
  * ctx.skip = true melewati kode asli. Dokumen tidak menjelaskan
    apa yang terjadi pada argumen/stack bila dipakai sembarangan.
  * Tidak ada dokumentasi tentang flag CPU (OF/CF/ZF). Padahal A3
    di Bagian D1 menyebut imul mengubah flag — jadi tidak ada cara
    yang TERDOKUMENTASI untuk memulihkannya lewat API ini.
------------------------------------------------------------------------------
KESIMPULAN: API-nya memberi AKSES ke r12, tetapi tidak memberi
BUKTI bahwa r12 berisi jumlah loot. Akses ≠ pemahaman.

     uji   : Dokumentasi Intel/AMD SDM. Tidak perlu dibuktikan ulang.
------------------------------------------------------------------------------
[TERBUKTI] A2     (arsitektur)
     klaim : Penulisan 32-bit ke register x86-64 menolkan bit 32..63, jadi imul pada R12D membuat R12 = zero-extend(R12D).
     uji   : Intel SDM Vol.1 §3.4.1.1 (64-bit mode register behavior).
------------------------------------------------------------------------------
[TERBUKTI] A3     (arsitektur)
     klaim : imul signed 32-bit overflow -> hasil terpotong 2^32 dan membalik tanda; flag OF/CF ikut berubah dan dapat mengubah percabangan (jo/jc) setelahnya.
     uji   : Intel SDM, instruksi IMUL. Dapat direproduksi di emulator.
------------------------------------------------------------------------------
[BELUM TERBUKTI] G1     (game)
     klaim : Pada titik hook tersebut, R12D berisi JUMLAH LOOT.
     uji   : Telusuri instruksi yang MENULIS R12D sebelum titik hook (backward slice). Bila sumbernya bukan argumen/field jumlah loot, klaim ini gugur.
------------------------------------------------------------------------------
[BELUM TERBUKTI] G2     (game)
     klaim : Nilai R12D di titik itu mengalir ke fungsi yang mengomit sumber daya (forward taint), tanpa konsumen lain di antaranya.
     uji   : Tandai nilai, lalu amati apakah ia sampai ke pembaruan inventori. Cek apakah R12 dipakai sebagai counter/pointer di antara titik hook dan commit.
------------------------------------------------------------------------------
[BELUM TERBUKTI] G3     (game)
     klaim : Titik hook dieksekusi tepat SATU KALI per kejadian drop (bukan per frame / per entitas / per tick).
     uji   : Pasang hit-counter pasif, bandingkan hit count dengan jumlah drop yang ter observe di layar.

[BELUM TERBUKTI] G4     (game)

A1e. ANALISIS ctx.r12 vs R12D (menjawab syarat #2 dan #4)
==============================================================================
TEMUAN DARI _docs.pluto:
  * OWH mengekspos ctx.r12 — yaitu register 64-bit penuh.
  * Dokumen TIDAK menyediakan ctx.r12d, ctx.r8d, ctx.eax, dst.
    Semua register diekspos dalam lebar 64-bit.

  Jadi 'R12D' yang kamu tanyakan = 32-bit RENDAH dari ctx.r12.
  Bukan sesuatu yang bisa diset langsung — harus dihitung.
------------------------------------------------------------------------------
KONSEKUENSI PENTING (mengacu pada A1/A2 di Bagian D1):
  1. Kalau kamu menulis nilai 32-bit ke r12, x86-64 MENOLKAN
     bit 32..63. Jadi bit atas yang tadinya tidak nol akan hilang.
  2. Kalau r12 menyimpan POINTER 64-bit dan kamu hanya memotong
     32-bit rendahnya, pointer itu HANCUR. Ini alasan kuat
     mengapa G1/G2 wajib dibuktikan lebih dulu.
  3. Menulis 32-bit rendah tanpa merusak bit atas butuh operasi
     masking, bukan sekadar perkalian.
------------------------------------------------------------------------------
CONTOH ARITMETIKA (murni hitungan, tidak menyentuh game):
  nilai 64-bit penuh : 4294967396  (bit atas=1, 32-bit rendah=100)
  low32 (R12D)       : 100
  ganti rendah jadi 300, bit atas dipertahankan -> 4294967596
  bandingkan: mengalikan SELURUH nilai 64-bit ikut mengubah bit atas
              (contoh: 4294967396 x3 = 12884902188)  <-- bukan yang diinginkan
------------------------------------------------------------------------------
CATATAN TAMBAHAN DARI DOKUMEN:
  * ctx.xmm0..xmm15 diekspos sebagai float 32-bit rendah.
    Kalau jumlah loot disimpan sebagai FLOAT, maka register yang
    relevan adalah xmm, BUKAN r12. Ini harus dibuktikan dulu.
  * ctx.skip = true melewati kode asli. Dokumen tidak menjelaskan
    apa yang terjadi pada argumen/stack bila dipakai sembarangan.
  * Tidak ada dokumentasi tentang flag CPU (OF/CF/ZF). Padahal A3
    di Bagian D1 menyebut imul mengubah flag — jadi tidak ada cara
    yang TERDOKUMENTASI untuk memulihkannya lewat API ini.
------------------------------------------------------------------------------
KESIMPULAN: API-nya memberi AKSES ke r12, tetapi tidak memberi
BUKTI bahwa r12 berisi jumlah loot. Akses ≠ pemahaman.
